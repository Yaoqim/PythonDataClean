##### 业务核心字段清洗流程

本章节详细说明7个业务核心字段的清洗策略：

**1. 商家名称 (merchant_name) - 核心**

- **数据来源**：原始数据中的店铺名/商家名
- **标准化处理**：
  - 归一化：建立标准商家库，匹配官方全称（如 "仕马旗舰店" -> "仕马汽车保养旗舰店"）
  - 去除冗余后缀：去除 "(拼多多店)", "(备用)" 等抓取标记
- **质量检验**：长度2-100字符，必填
- **准确度评估字段**：merchant_name_anal (0-100分) + merchant_name_anal_info (归一化匹配算法说明)

**2. 客户名称 (customer_name) - 核心**

- **数据来源**：原始数据中通常为昵称/账户名
- **脱敏处理**：
  - 真实姓名 → "客户_" + 哈希后缀
  - 手机号 → "****"
  - 身份证号 → 完全删除
  - 保留账户后4位以便对账
- **缺失处理**：填充"匿名客户"
- **质量检验**：长度0-50字符
- **准确度评估字段**：customer_name_anal (0-100分) + customer_name_anal_info (评估说明)

**3. 客服名称 (agent_name) - 核心**

- **数据来源**：原始数据通常为客服工号或昵称
- **标准化处理**：
  - 统一格式为"客服_工号"或"客服_昵称"
  - 缺失则标记"自动客服"
- **质量检验**：长度0-30字符
- **准确度评估字段**：agent_name_anal (0-100分) + agent_name_anal_info (评估说明)

**4. 消息类型 (message_type) - 核心**

- **数据来源**：
  - 优先从原始数据提取（如淘宝、企业客服系统已标注）
  - 若原始数据无标注，根据上下文推导
- **标准化字典（中文）**：
  - 客户消息
  - 客服回复
  - 系统消息
  - 转移通知
  - 其他
- **推导规则**（无标注时）：
  - 检查消息发送者字段：user_id→"客户消息"，agent_id→"客服回复"
  - 检查消息内容：包含系统关键词→"系统消息"
  - 无法判定→"其他"
- **质量检验**：必填，仅限上述5个值
- **准确度评估字段**：message_type_anal (0-100分) + message_type_anal_info (标注来源：原始数据/推导规则/置信度)

**5. 消息内容 (message_content) - 核心**

- **清洗流程**（Python实现）：
  1. 去HTML标签（BeautifulSoup或正则）
  2. 去emoji和特殊表情（emoji库）
  3. 去URL链接和@符号（正则表达式）
  4. 统一编码为UTF-8
  5. 长度限制≤5000字符，超长截断
- **异常处理**：
  - 全是污染 → 标记"content_invalid" → 删除
  - <5字 → 标记"content_too_short"（可保留）
  - 乱码无法修正 → 标记"encoding_error" → 删除
- **复杂语义需求**（调用大模型）：
  - 消息内容去污後仍不可读
  - 需要识别客户隐含需求
  - 投诉情感分析（见sentiment字段）
- **准确度评估字段**：message_content_anal (0-100分) + message_content_anal_info (清洁方式/污染处理记录)

**6. 消息时间 (message_time) - 核心**

- **标准格式**：YYYY-MM-DD HH:MM:SS
- **清洗规则**（Python实现）：
  1. 解析多种时间格式（相对时间→绝对时间）
  2. 时间校验：message_time >= conversation_start_time 且 <= 当前时间
  3. 按message_time排序，检测>1小时时间跳变
  4. 去重：相同消息时间戳标记
- **异常处理**：
  - 晚于当前时间 → 标记"time_invalid" → 删除
  - 逆序排列 → 重新排序，标记"message_order_uncertain"
  - 时间跳变>1小时 → 标记"time_gap_detected"（保留）
- **质量检验**：必填，格式校验
- **准确度评估字段**：message_time_anal (0-100分) + message_time_anal_info (格式转换规则/时间异常标记)

**7. platform (platform) - 核心**

- **标准化字典（中文）**：
  - 微信
  - 淘宝
  - 企业QQ
  - 钉钉
  - 客服热线
  - 邮件
  - 未知
- **清洗规则**（Python实现）：
  1. 从原始数据字段提取
  2. 统一为上述标准字典值
  3. 无法识别 → "未知"
- **多平台特异性处理**：
  - 微信：去emoji、特殊转义
  - 淘宝：保留订单号关联
  - 客服热线：保留转录精度评分
  - 邮件：去HTML签名
- **质量检验**：必填，仅限上述7个值
- **准确度评估字段**：platform_anal (0-100分) + platform_anal_info (平台识别来源/特异性处理标记)

##### 特殊字段处理说明

**1. 对话主题 (conversation_topic) - 标签字段**

- **实现方式**：关联到独立标签表 `customer_conversation_tag`
- **标签来源**：
  - 从消息内容自动提取（关键词匹配或大模型分类）
  - 标签值示例：订单问题、退货申请、投诉、咨询、售后支持等
- **标签管理**：在customer_conversation_tag表中维护
  - 主键：(conversation_id, tag_value)
  - 包含tag_confidence字段

**2. 情感倾向 (sentiment) - 大模型清洗**

- **标准化字典（中文）**：
  - 正面
  - 中立
  - 负面
- **清洗方式**：大模型分析（Python基础规则不适用）
  - 输入：清洗后的message_content
  - 输出：情感分类 + 置信度
- **质量检验**：仅限上述3个值

**3. 对话状态 (conversation_status)**

- **标准化字典（中文）**：
  - 进行中
  - 已结束
  - 已转移
  - 等待中
- **填充规则**：从原始数据或业务规则推导

**4. 解决时长 (resolution_time) - 可选字段**

- **填充条件**：仅在对话最后一条消息时填充
- **计算方式**：最后消息时间 - 首条消息时间（分钟数）
- **缺失处理**：进行中的对话为NULL

**5. 满意度 (satisfaction) - 可选字段**

- **填充条件**：仅在对话结束时填充
- **数据来源**：原始数据中的满意度评分或客户评价
- **标准化**：统一为1-5数字评分
- **缺失处理**：结束未评价的对话为NULL

##### 常见问题与清洗方案

**第一阶段：对话记录验证与去重**

| 问题类型        | 具体表现                       | 清洗方案                                                                         | 执行步骤                                                                                          | 无法清洗处理                                           |
| --------------- | ------------------------------ | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| 重复对话        | 相同conversation_id或内容重复  | 按conversation_id分组去重，检测完全重复的对话记录                                 | 1. 分组统计重复 2. 检测时间范围 3. 保留最早记录 4. 标记重复关系                                   | 若无conversation_id，按时间+user_id+首条消息判断，标记"redup_detected" |
| conversation_id 缺失 | 对话无唯一标识                 | **补充策略**：由(customer_name, message_time, platform)组合生成哈希ID             | 1. 组合关键字段 2. SHA256哈希生成临时ID 3. 检验唯一性 4. 标记"id_generated"                       | 若组合字段不完整 → 标记"critical_missing" → 删除       |
| 消息顺序混乱    | 消息时间戳不按时间排序         | 按message_time重新排序、检测异常时间差                                             | 1. 按message_time排序 2. 检测>1小时的时间跳变 3. 标记异常顺序 4. 重新排列                         | 时间无法修正 → 标记"message_order_uncertain" → 留待审核 |
| 核心字段缺失(customer_name/agent_name/message_type) | 核心字段无数据 | 根据字段特性采用不同补充策略或删除 | 见业务核心字段清洗流程章节 | 无法补充 → 删除此消息或对话 |

**第二阶段：核心字段内容清洗与补充**

| 问题类型       | 具体表现                    | 清洗方案 | 执行步骤 | 处理方式 | 无法清洗处理 |
| -------------- | ----------------------------- | --------- | --------- | --------- | ------- |
| message_type缺失 | 原始数据未标注消息类型 | 根据上下文推导：① 检查消息发送者字段(user_id/agent_id) ② 检查系统关键词 ③ 无法判定→"其他" | 1. 获取发送者身份 2. 应用推导规则 3. 标记推导来源 | 标准化为中文值(客户消息/客服回复/系统消息/转移通知/其他) | 无法推导 → 标记"message_type_unknown" → 删除 |
| message_content污染 | HTML标签、emoji、链接等 | 分步清洗(Python)：① 去HTML ② 去emoji ③ 去URL ④ 去@符号 | 1. BeautifulSoup去HTML 2. emoji库处理 3. 正则删除 | 清洗后长度>5字才保留 | 全污染 → 标记"content_invalid" → 删除 |
| platform值不统一 | 原始数据为英文或混乱格式 | 规范化为中文标准值 | 1. 识别原始值 2. 映射到标准字典 3. 标记"platform_normalized" | 中文值(微信/淘宝/企业QQ/钉钉/客服热线/邮件/未知) | 无法识别 → 标记"platform_error" → 删除 |
| message_time格式混乱 | 多种时间格式混存 | 统一转换为YYYY-MM-DD HH:MM:SS | 1. 解析时间格式 2. 相对→绝对转换 3. 时间校验 | 标记转换规则，排序检测 | 时间无法修正 → 标记"time_invalid" → 删除 |
| 消息内容短于5字 | "好的"、"谢谢"等简短回复 | 保留，仅标记"content_too_short" | 1. 计算长度 2. <5字标记 3. 保留原文 | 保留原文，业务自行决定是否使用 | - |
| 编码乱码 | 出现不可读字符 | chardet检测→重新解码为UTF-8 | 1. chardet识别编码 2. 解码 3. 验证汉字可读性 | UTF-8编码可读 | 编码识别失败 → 标记"encoding_error" → 删除 |

**第三阶段：非核心字段处理**

| 字段名 | 数据来源 | 清洗方式 | 备注 |
| ------ | ------- | ------ | ---- |
| conversation_topic(对话主题) | 消息内容自动提取 | 标签关联：写入customer_conversation_tag表 | 支持多标签 |
| sentiment(情感倾向) | 大模型分析 | 调用大模型对清洗后的message_content进行情感分类 | 标准化为中文(正面/中立/负面) |
| conversation_status(对话状态) | 原始数据或推导 | 映射到标准字典(中文) | 进行中/已结束/已转移/等待中 | 
| resolution_time(解决时长) | 消息时间戳计算 | 仅最后消息填充：末消息时间-首消息时间(分钟) | 进行中对话为NULL |
| satisfaction(满意度) | 原始评分数据 | 仅最后消息填充，标准化为1-5 | 结束未评价为NULL |

**第四阶段：异常值检测与修正**

| 问题类型 | 具体表现 | 检测方法 | 处理方式 |
| ------ | ------ | ------ | ------ |
| 时间逆序 | 消息时间戳不递增 | 比较相邻消息时间 | 按message_time重新排序，标记"message_order_fixed" |
| 时间跳变 | 相邻消息间隔>1小时 | 计算时间差 | 标记"time_gap_detected"，保留消息 |
| 消息内容冲突(复杂语义) | 客服回复与问题完全无关 | 调用大模型相似度分析 | 相似度<0.3标记"logic_conflict"，人工审核 |
| 对话无效期超期 | 对话超过规定有效期(30-90天) | (当前时间-末消息时间) | 标记"expired_conversation"，但保留数据 |

---

#### 五、Python清洗流程详解

##### 第一步：message_content清洁
1. 去HTML标签、去emoji表情、去URL链接、去@提及
2. 删除\\n、\\r、\\t等特殊转义序列
3. 编码规范化为UTF-8、去多余空格
4. 长度检查：清洁后不超过5000字符、保留申记
5. 输出：清洁后内容+状态(success/invalid)+警告

##### 第二步：message_time解析与验证
1. 相对时间转绝对时间（检测离散、刚刚等）
2. 尝试多种格式解析(YYYY-MM-DD HH:MM:SS、相对时间等)
3. 时间范围校验、时序一致性检测、异常间隔检测(>1小时)
4. 统一输出为YYYY-MM-DD HH:MM:SS

##### 第三步：message_type推导
1. 优先从原始数据提取（置信度0.95）
2. 根据发送者身份判断：user_id→"客户消息"、agent_id→"客服回复"
3. 系统关键词检测→"系统消息"、转移指示→"转移通知"
4. 无法判定→"其他"

##### 第四步：platform标准化
1. 从源数据提取，映射到标准中文：微信/淘宝/企业QQ/钉钉/客服热线/邮件/未知
2. 无法识别→"未知"

##### 第五步：核心字段质量检查
检查customer_name/agent_name/message_type/message_content/message_time/platform是否符合业务规范。若任何一个核心字段失效，则删除此消息或对话

---

#### 六、大模型清洗流程详解

##### 任务1：情感倾向分析(LLM)
提示词需要：详细解释正面(满意/感谢/认可/积极)、中立(事实/询问/一般)、负面(不满/投诉/批评/消极)的定义

返回格式(JSON)：sentiment(中文)+confidence(0-100)+keywords+reasoning

质量管理：置信度<70时触发所指处理

##### 任务2：对话主题分类(LLM)
预定义标签：订单问题/退货申请/投诉/咨询/售后支持/物流查询/其他(中文，支持一条消息多个标签)

返回格式(JSON)：topics(数组)+confidence+topic_details+reasoning

质量管理：结果存入customer_conversation_tag表，每个标签管理置信度

##### 任务3：消息相似度检测(LLM)
客户消息+客服回复的相似度：90-100完全相关/70-89相关/50-69部分相关/0-49完全无关

返回格式(JSON)：similarity_score(0-100)+is_relevant(布尔)+reasoning

质量管理：<0.3标记"logic_conflict"，需人工审核

##### LLM调用需求
1. 提示词全部中文化：选项、返回值等
2. 批量优化：一次提示张挂一条消息，减少调用次数
3. 置信度阈值：根据业务重要性设定、触发所指处理
4. 错误降级：失败时返回ERROR状态或null，不中断清洁
5. 返回格式：所有输出JSON结构化

---

#### 七、混合清洁流程

**执行顺序**：Python规则清洁 → LLM语义分析 → 质量检查 → 异常处理 → 结果列表

每条消息输出：程序状态(status)+警告信息(warnings)+置信度(confidence)+提取原因

### 九、 数据交付格式指南 (Data Delivery Format Guide)

针对不同规模的对话数据，建议采用以下交付格式以平衡结构清晰度与处理效率：

#### 9.1 小规模数据 (JSON)
- **适用场景**: 开发测试、Demo 展示、少于 1000 条会话。
- **格式要求**:
  - 采用层级嵌套结构，以会话（Session）为顶级对象，消息（Messages）为子数组。
  - **精简原则**: 若 `messages` 数组中已包含明确的 `sender`（发送者）和 `agent_type`（客服类型），则会话级的 `customer_name` 和 `agent_name` 字段应省略，避免冗余并保持结构清晰。
  - **必须字段**: `conversation_id`, `merchant_name`, `platform`, `messages`。
- **示例结构**:
  ```json
  {
    "conversation_id": "S1001",
    "merchant_name": "示例店铺",
    "platform": "微信",
    "messages": [
      { "sender": "张三", "content": "你好", "timestamp": "2026-01-12 10:00:00" },
      { "sender": "小李", "content": "您好", "timestamp": "2026-01-12 10:00:05", "agent_type": "人工" }
    ]
  }
  ```

#### 9.2 中/大规模数据 (Excel)
- **适用场景**: 批量生产环境导入、大规模人工质检、多于 1000 条会话。
- **格式要求**:
  - 必须采用**扁平化结构**（Flat Structure），即 Excel 中的每一行代表一条独立的消息。
  - 会话级的元数据（如商家名、平台）在每一行中重复出现。
  - **核心约束**: Excel 文件中必须包含 `conversation_id` 列，用于标识每条消息所属的对话。所有属于同一个对话的消息，其 `conversation_id` 值必须相同，以此来聚合属于同一对话的多条消息记录。
  - **表头规范 (Headers)**:

| 表头字段 | 说明 | 必填 | 示例 |
| :--- | :--- | :--- | :--- |
| conversation_id | 会话唯一标识 | 是 | PDD_992831 |
| merchant_name | 商家/店铺名称 | 是 | 仕马汽车保养旗舰店 |
| sender | 发送者名称/昵称 | 是 | 蜜**熊 |
| agent_type | 客服类型 | 否 | 人工 / 机器人 |
| content | 消息内容 | 是 | 亲，有什么可以帮您？ |
| timestamp | 发送时间 | 是 | 2026/1/12 10:05 |
| platform | 来源平台 | 是 | 拼多多 |
| product_name | 涉及商品 | 否 | 玻璃水 |
| user_id | 客户唯一ID | 否 | U88271 |

- **注意事项**: 
  - 时间格式建议统一为 `YYYY-MM-DD HH:MM:SS` 以减少解析偏差。
  - 消息内容中若包含换行符，应在导出时进行转义或使用双引号包裹，防止 CSV 错行。
