#### 2.1 社交平台评论（微博、知乎、小红书、B 站）

**数据特征**：结构化（JSON）/半结构化（HTML），单内容 500-100000 条评论，高难度

**业务字段清单**：comment_id, post_id, user_name, comment_content, like_count, comment_time, platform

**业务核心字段**：comment_id(主键), post_id, comment_content, comment_time, platform

##### 字段详细说明表

| 英文字段名      | 中文名   | 来源性质 | 处理方式                                               | 说明                       |
| --------------- | -------- | -------- | ------------------------------------------------------ | -------------------------- |
| comment_id      | 评论 ID  | 原始     | 去特殊字符、按平台规范化                               | 评论唯一标识               |
| post_id         | 帖子 ID  | 原始     | 格式转换、按平台规范化                                 | 所属内容 ID                |
| user_id         | 用户 ID  | 原始     | **不指簀使用**，见说明 | 用户唯一标识（应缺失或距简user_name）|
| user_name       | 用户名   | 原始     | 去emoji和装饰符，缺失填充"匿名"                      | 用户昵称（脱敏数据）       |
| comment_content | 评论内容 | 处理后   | 去 HTML 标签、#话题#、@用户、表情、URL、限制 ≤10000 字 | 核心内容，需详细清洗       |
| like_count      | 点赞数   | 处理后   | 去非数字，换算单位("5 万"→50000)，转整数               | 互动自然，需检测异常       |
| comment_time    | 评论时间 | 处理后   | 相对 → 绝对时间，统一 YYYY-MM-DD HH:MM:SS              | 可为"刚刘""、"1 小时前"    |
| platform        | 平台     | 新增     | 平台标识(weibo/zhihu/xiaohongshu/bilibili)             | 区分不同平台               |
| is_spam         | 是否垃圾 | 新增     | 垃圾评论标记(0/1)                                      | 启用基于内容与上下文的检测 |
| is_repost       | 是否转载 | 新增     | 转载/转发评论标记(0/1)                                 | 同一评论转发需去重         |
| clean_time      | 清洗时间 | 新增     | 清洗完成时间                                           | 应用 timestamp             |

##### 特殊字段处理说明

**1. 平台处理统一性**

不同平台需要按规范转换标准：

- 若 parent_comment 存在性检查失败，执行 30% 的准确度的渐进
平台   user_id格式    user_name    comment_time
微博   整数       @昵称      2024-01-08 15:30:00
知乎   字母数字  昵称      相对时间传绝对
小红书 整数      昵称      相对时间

**2. 文本污染清洗**

各平台需去除特定污染：

- 微博：#话题#、转发、@用户
- 知乎：分类信息、@用户
- 小红书：商品推广、微商代理

**3. 垃圾评论模式**

检测：高频重复字符、纯外部链接、客服联系、上下文完全不相关

##### 分步骤清洗流程

**第一阶段：去重与关键字段验证**

| 问题类型        | 具体表现                       | 清洗方案                                                                         | 执行步骤                                                                                          | 无法清洗处理                                           |
| --------------- | ------------------------------ | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| 重复评论        | 相同 comment_id 或内容完全重复 | 按 comment_id 分组去重，或按(post_id, user_name, content)组合检测                  | 1. 分组统计重复 2. 检测内容相似度 3. 保留最早发布的评论 4. 标记重复关系                           | 若无 comment_id，按内容组合判断，标记"repost_detected" |
| comment_id 缺失 | 评论无唯一标识                 | **补充策略**：由(post_id, user_name, comment_content, comment_time)组合生成哈希 ID | 1. 组合关键字段 2. SHA256 哈希生成临时 ID 3. 检验唯一性 4. 标记"id_generated"                     | 若组合字段不完整 → 标记"critical_missing" → 删除       |
| post_id 缺失    | 评论无关联内容                 | **补充策略**：从网页来源推断或查询相邻评论                                       | 1. 检查 HTTP Referer 2. 查询相邻评论的 post_id 3. 多数投票补充 4. 标记"post_id_supplemented"      | 无法推断 → 标记"post_id_unavailable" → 删除            |
| user_id 缺失    | 匿名/游客评论                  | **不推荐补充user_id**。建议仅保流user_name代止（见说明）                                          | 1. 检查 user_name 2. 缺失不填充 3. 仅保流 user_name              | 仅应用user_name       |

**第二阶段：字段内容清洗与补充**

| 问题类型       | 具体表现                                      | 清洗方案                                                                                                                 | 执行步骤                                                                                             | 准确性评估                            | 无法清洗处理                                    |
| -------------- | --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------- | ------------------------------------- | ----------------------------------------------- |
| 平台特异性差异 | user_id 格式(微博整数/知乎字母数字)、时间格式 | 按 platform 字段分别处理：微博去@符、知乎字母保留、小红书整数规范化                                                      | 1. 识别 platform 值 2. 按规则提取 user_id 3. 保留原始格式备份 4. 标记"platform_normalized"           | 不同平台规范一致性 >=85%              | 格式无法识别 → 标记"platform_error"             |
| 文本污染       | HTML 标签、#话题#、@用户、转发、表情、URL     | 分步清洗：① 去 HTML 标签(BeautifulSoup) ② 去#话题#标签 ③ 去@用户提及 ④ 去转发标记("转发自") ⑤ 去 emoji 表情 ⑥ 去链接 URL | 1. BeautifulSoup 解析 HTML 2. 正则表达式去污 3. emoji 库检测去除 4. URL 正则删除 5. 验证清洗后文本>0 | 清洗后文本长度>5 且可读性评分>60%     | 全是污染 → 标记"content_invalid" → 删除         |
| 评论过短       | comment_content < 5 字                        | 检测并标记，可选删除或保留                                                                                               | 1. 计算文本长度 2. <5 字则标记"content_too_short" 3. 业务判断是否删除(如"好""赞"仍有价值)            | 是否有实际语义价值(含有态度词/感情词) | 根据业务规则决定保留或删除                      |
| 垃圾评论       | 高频重复字符、纯广告、无关内容、刷屏          | 检测多维度特征：① 连续字符重复率>80% ② 广告关键词比例>30% ③ 与 post 内容相关度<0.3                                       | 1. 计算重复率 2. 关键词匹配 3. NLP 相似度计算 4. 综合判定 5. 标记"spam_detected"                     | 识别准确度 >=85%                      | 判定不确定 → 标记"spam_suspicious" → 待人工审核 |

**第三阶段：异常值检测与修正**

| 问题类型               | 具体表现                                       | 清洗方案                                                 | 执行步骤                                                                       | 异常判定标准                                 | 无法清洗处理                                     |
| ---------------------- | ---------------------------------------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------ | -------------------------------------------- | ------------------------------------------------ |
| like_count 异常        | 负数、超百万(999999)、超过理论上限             | 范围检验(≥0, ≤1000000)，超出范围标记"like_count_invalid" | 1. 检验数值范围 2. 检测是否为默认填充值 3. 异常则标记 4. 可选删除              | 标准范围 0-1000000；>1000000 判为异常        | 无法修正 → 标记"like_count_unknown"              |
| 时间异常               | 时间早于 post 发布时间、晚于当前时间、格式混乱 | 时间范围校验：comment_time >= post_time 且 <= 当前时间   | 1. 解析时间格式 2. 与 post_time 比对 3. 与当前时间比对 4. 格式转换 5. 标记异常 | 逻辑范围：post_time <= comment_time <= now() | 时间无法修正 → 标记"time_invalid" → 删除         |
| user_location 格式混乱 | 缺失、格式不一致("北京朝阳"vs"北京市朝阳区")   | 规范化为"省-市-区"格式，建立地点库映射                   | 1. 检测地点格式 2. 按地点库匹配标准化 3. 缺失则填充"未知" 4. 标记来源          | 标准化成功率 >=90%                           | 无法匹配 → 保留原始值，标记"location_unstandard" |

**第四阶段：文本清洗与编码处理**

| 问题类型 | 具体表现             | 清洗方案                                                  | 执行步骤                                                                      | 验证方式                 | 无法清洗处理                               |
| -------- | -------------------- | --------------------------------------------------------- | ----------------------------------------------------------------------------- | ------------------------ | ------------------------------------------ |
| 乱码文本 | 评论内容出现乱码字符 | 使用 chardet 检测原始编码 → 重新解码为 UTF-8 → 验证可读性 | 1. chardet 检测编码 2. 按检测编码解码 3. 验证汉字可读性 4. 失败则尝试其他编码 | 解码后不含乱码且汉字可读 | 编码无法识别 → 标记"encoding_error" → 删除 |
| 超长评论 | 超过 10000 字        | 截断至 10000 字，标记"content_truncated"                  | 1. 检测长度 2. >10000 则截断 3. 保存原始长度到 metadata 4. 标记截断           | 截断位置是否损失关键信息 | 手工评估是否需保留全文                     |

##### 缺失值补充策略汇总

**分级补充方案**（按准确性从高到低）：

| 缺失字段         | 一级补充(>95%)    | 二级补充(70-95%)                  | 外部补充(<70%)  | 补充失败处理                      |
| ---------------- | ----------------- | --------------------------------- | --------------- | --------------------------------- |
| **comment_id**   | 源系统 comment_id | 生成(post_id+user_name+content)哈希 | 序列号+platform | **无法补充** → 删除               |
| **post_id**      | 源系统 post_id    | HTTP Referer 推断                 | 相邻评论推断    | **无法补充** → 删除               |
| **user_id**      | 源系统 user_id    | **不推荐使用** | 业务表建议不存储 user_id，不需补充 | **标记 user_id_unavailable** → 仅用 user_name         |
| **like_count**   | 原始互动数        | 相似内容平均值                    | 填充 0          | **标记 like_count_unknown**       |
| **comment_time** | 源系统时间戳      | 相对时间转绝对                    | 填充发布日期    | **标记 time_uncertain**           |

**准确性评估指标**：

- 若 parent_comment 存在性检查失败，执行 30% 的准确度的渐进
comment_quality = Σ(field_weight × field_confidence) / Σfield_weight

字段权重分配：
  comment_id: 1.0 (必填)
  post_id: 1.0 (必填)
  user_id: 0.8 (关键)
  comment_content: 0.9 (关键)
  like_count: 0.4 (可选)
  comment_time: 0.6 (重要)
  platform: 0.5 (辅助)

判定标准：
  >= 80%: 优质评论，可直接使用
  >= 60%: 良好评论，可使用但需标记
  >= 40%: 一般评论，需要审核
  < 40%: 低质评论，建议删除

**存储建议**：

- 表名：`social_comment`
- 主键：`comment_id`
- 索引：`(post_id, user_id, comment_time, platform)`
- 全文索引：`comment_content`
- 分区：按 platform + comment_date
