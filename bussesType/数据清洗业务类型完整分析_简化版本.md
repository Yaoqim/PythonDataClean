## 业务类型全景分类

根据业务场景、数据结构、清洗需求，可将**已初步处理的结构化数据**分为以下业务类型：

### 数据结构定义说明

| 数据结构类型 | 定义 | 对应文件格式 | 特征 | 清洗复杂度 |
| --- | --- | --- | --- | --- |
| **结构化** | 数据以表格或固定模式组织，字段定义明确、格式规范 | JSON、CSV、XML、SQL 数据库记录 | 字段类型明确、易于解析、值域清晰 | 低-中 |
| **半结构化** | 数据具有部分结构特征，某些字段结构化、某些字段文本化 | JSON（混合嵌套对象和文本）、HTML 表格、富文本 | 混合字段类型、需要字段分离、文本和结构共存 | 中-高 |
| **非结构化** | 数据以自由文本形式存储，无预定义字段和格式 | TXT、PDF、DOC、HTML 正文、长文本 | 需要自然语言处理、信息提取困难、格式多样 | 高-特高 |

### 临时存储格式选择指南

| 业务特征 | 推荐格式 | 适用场景 | 优势 | 权衡 |
| --- | --- | --- | --- | --- |
| 结构化、小规模（<10MB） | JSON | 企业工商、招聘岗位 | 格式简洁、易处理 | 存储体积较大 |
| 结构化、中等规模（10-500MB） | CSV/Parquet | 电商商品、房产信息 | Parquet压缩率高、查询快 | 需Parquet库支持 |
| 结构化、大规模（>500MB） | Parquet/JSONL分片 | 房产评论、房产信息百万级 | 列式存储、高压缩率 | 不适合行级修改 |
| 半结构化、高频I/O | JSONL（行式JSON） | 社交评论、资讯文章、商品评论 | 支持流式处理、行级独立 | 无法直接列式查询 |
| 非结构化、超大规模 | 分片+索引 | PDF财报、长文本 | 分片独立处理 | 需建立索引管理 |

## 通用的关键字段准确度评估机制

为了量化数据清洗的有效性，本项目为**每个业务类型的所有关键字段**建立了准确度评估机制。当关键字段缺失时，通过其他数据源的推导或分析方法补充数据，同时需要评估补充后数据的可信度。

### 全局知识索引与标识机制 (Global Knowledge Index Mechanism)

在“四位一体”知识中枢架构中，`knowledge_id` 是连接所有存储系统的唯一纽带。为了实现跨业务、跨系统的高效调度与溯源，必须建立全局统一的知识索引表。

#### 1. 核心设计原则
- **全局唯一性**：使用 `BIGINT` 类型，支持海量数据（可扩展至 Snowflake 雪花算法）。
- **解耦性**：索引表记录元数据路径，业务表记录详细事实，实现逻辑隔离。
- **一致性控制**：记录各库（MySQL, OSS, Milvus, Neo4j）的同步状态，防止数据孤岛。

#### 2. 全局索引表结构定义 (SQL)

```
CREATE TABLE `knowledge_index` (
  -- 核心标识
  `knowledge_id` BIGINT AUTO_INCREMENT PRIMARY KEY COMMENT '全局唯一知识ID',
  `business_type` TINYINT NOT NULL COMMENT '业务类型代码(如: 1-电商, 2-资讯)',
  `data_source` VARCHAR(50) NOT NULL COMMENT '数据来源标识(如: jd, weibo)',
  `original_id` VARCHAR(100) NOT NULL COMMENT '源平台原始唯一标识',
  
  -- 存储映射
  `mysql_table` VARCHAR(64) NOT NULL COMMENT '对应业务表的表名',
  `oss_root_path` VARCHAR(255) NOT NULL COMMENT '在OSS中的根存储路径',
  `milvus_collection` VARCHAR(64) COMMENT '对应的向量集合名称',
  `neo4j_label` VARCHAR(64) COMMENT '图数据库中的核心节点标签',
  
  -- 状态与质量
  `process_status` TINYINT DEFAULT 0 COMMENT '处理状态: 0-采集, 1-已清洗, 2-向量化完成, 3-全库入库',
  `quality_score` DECIMAL(5, 2) COMMENT '全局质量综合评分',
  
  -- 审计
  `created_at` DATETIME DEFAULT CURRENT_TIMESTAMP COMMENT '首次创建时间',
  `updated_at` DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '最后同步时间',
  
  -- 约束与索引
  UNIQUE KEY `idx_source_original` (`business_type`, `data_source`, `original_id`),
  KEY `idx_status` (`process_status`),
  KEY `idx_created_at` (`created_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='全局知识索引表-知识中枢的元数据根目录';
```

### 数据演进与版本控制协议 (Data Evolution & Versioning)

针对每日高频抓取、核心字段变更以及价格/评分波动，系统采用“双哈希控制”与“敏感度分级”策略。

#### 1. 双哈希控制机制 (Dual-Hash Control)

为了精准判断是否需要触发高昂的 LLM 打标或向量更新，引入两个逻辑哈希：

- **语义哈希 (Semantic Hash)**：由 `title`, `brand`, `model`, `spec_params` 等决定语义的字段组成。
  - **触发条件**：若语义哈希变化，**必须**重走打标流程，更新 Milvus 向量和 Neo4j 拓扑。
- **事实哈希 (Fact Hash)**：由 `price`, `sales_volume`, `rating`, `good_rate` 等纯属性字段组成。
  - **触发条件**：若仅事实哈希变化，仅更新 MySQL 记录和 Neo4j 节点属性，不重新生成向量。

#### 2. 版本控制规则 (Versioning Rules)

- **版本号 (`version`)**：仅在“语义哈希”发生实质性变更时升级。
  - **示例**：iPhone 19 修改为 iPhone 19 Plus。
- **更新时间 (`updated_at`)**：无论任何字段变化，只要数据有更新（如每日价格波动），即刷新该时间。
- **历史快照**：OSS 中的 `raw_source.json` 按日期分片存储，永久保留每一天的原始快照，MySQL 仅保留“当前最新态”。

#### 3. 典型场景处理方案 (Typical Scenarios)

| 场景描述 | 判定类型 | 处理动作 (Action) |
| :--- | :--- | :--- |
| **微小文案修正** (如: iphone -> iPhone) | 语义不变 | 归一化处理。语义哈希对比一致 -> **仅更新 MySQL**。 |
| **核心实体变更** (如: iPhone 19 -> 19 Plus) | 语义变更 | **全库联动**。更新 MySQL，重刷 Milvus 向量，重连 Neo4j 关系。 |
| **高频数值波动** (如: 双11价格/评分日更) | 事实变更 | **局部同步**。更新 MySQL 核心值，刷新 `price_anal` 评分，不动向量。 |
| **质量评估变化** (如: 评分下降, 评论暴增) | 质量演进 | **重算总分**。更新 `quality_score`，若低于阈值则触发 `abnormal_tag`。 |

### 通用评估字段结构（以任意关键字段为例，如 field_name）

| 字段维度 | 字段名 | 类型 | 说明 |
| --- | --- | --- | --- |
| 原始字段 | field_name | 根据业务类型定义 | 实际数据值（原始值或补充后的值） |
| 准确度评分 | field_name_anal | 整数(0-100) | 该字段的数据准确度量化评分 |
| 准确度描述 | field_name_anal_info | VARCHAR(500) | 详细说明该字段的准确度来源、计算方法和评估过程 |

### 通用准确度评估计算公式

```
field_accuracy_score = (data_source_reliability × 0.4) 
                     + (logical_consistency × 0.3) 
                     + (external_validation_match × 0.3)

其中：
  data_source_reliability: 数据源权威性评分 (0-100)
    - 源系统提供的原始值: 95-100分
    - 历史版本推断: 75-85分
    - 外部库推算: 60-75分
    - 默认填充: 30-50分
  
  logical_consistency: 业务逻辑一致性检验 (0-100)
    - 与相关字段逻辑关系完全吻合: 90-100分
    - 基本符合业务逻辑: 70-89分
    - 存在轻微矛盾: 50-69分
  
  external_validation_match: 外部验证匹配度 (0-100)
    - 与官方库匹配率 > 95%: 90-100分
    - 与第三方数据匹配率 > 85%: 75-89分
    - 与相似记录对比: 60-74分
```

### 通用准确度阈值标准与处理方案

| 准确度范围 | 等级 | 自动处理 | 说明 |
| --- | --- | --- | --- |
| ≥ 85% | 优秀(Excellent) | ✅ 自动采用 | 数据质量高，直接进入正式库 |
| 70-84% | 良好(Good) | ⚠️ 标记待审核 | 标记为"存疑"或"需人工抽检"，定期进行样本验证 |
| 50-69% | 一般(Fair) | 🔍 人工验证 | 进入审核队列，由业务专家确认后导入 |
| < 50% | 较差(Poor) | ❌ 标记不可用 | 进入异常库，不参与业务分析，需重新处理或删除 |

### field_name_anal_info VARCHAR文本示例

`field_name_anal_info` 是VARCHAR(500)的文本字段，用于记录字段准确度评估的详细信息。以下是示例：

```

```

场景2（推导值 - 中等准确度）：

## 清洗流程通用方案

无论处理何种数据类型，清洗流程统一遵循以下 **5 大核心步骤**：

### 步骤 1：明确清洗目标

- 查看元数据清单，确定`must_clean_fields`（必清洗字段）
- 查看业务字典中的`field_standard_rule`（标准化规则）
- 聚焦核心字段，避免无效处理

### 步骤 2：去重处理

- 按唯一标识（如商品 ID、评论 ID）进行精准去重（优先级最高）
- 检测完全重复记录（所有字段内容一致）
- 生成去重统计报告

### 步骤 3：字段标准化

- **文本字段**：去空格、去特殊字符、统一编码、统一大小写
- **数值字段**：去单位、转为标准类型、范围校验
- **时间字段**：相对 → 绝对、统一格式、时间戳校验
- **分类字段**：规范化值、建立标准库、多值处理
- **URL/链接**：格式验证、失效检测

### 步骤 4：缺失值处理

- **核心字段**：缺失率低 → 删除记录，缺失率高 → 标注"待补充"
- **非核心字段**：填充"未知"、众数、中位数或 NULL
- 记录缺失统计

### 步骤 5：异常值修正

- **数值异常**：检测业务逻辑合理范围，用中位数/平均值修正，极端异常删除
- **格式异常**：尝试修复格式，无法修复则删除或标注
- **内容异常**：检测垃圾内容、广告内容，直接剔除或标记
- **关系异常**：如资产 ≠ 负债+权益，检测并标记
