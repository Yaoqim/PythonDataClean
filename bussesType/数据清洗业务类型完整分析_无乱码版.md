## 核心业务类型详细分析

### 一、电商平台数据

#### 1.1 电商商品信息

**数据特征**：半结构化（HTML）/ 结构化（JSON 接口），10-10000 条/批次

**关键字段清单**：product_id, source_platform, title, product_tags, price, original_price, currency_code, brand, category, spec_params, sales_volume, comment_count, rating, good_rate, shop_name, shop_id, is_official, listing_time, update_time

##### 字段详细说明表

| 英文字段名      | 中文名    | 来源性质 | 处理方式                                        | 说明                                      |
| --------------- | --------- | -------- | ----------------------------------------------- | ----------------------------------------- |
| product_id      | 商品 ID   | 原始     | 去首尾空格，保留纯数字                          | 商品在平台的唯一标识符                    |
| source_platform | 来源平台  | 原始     | 规范化平台名(jd/taobao/suning/pdd)              | 商品来自哪个电商平台                      |
| title           | 商品标题  | 原始     | 去 HTML 标签、特殊字符、统一编码、截断 200 字   | 可能含内嵌平台标记（如【官方旗舰店】）    |
| product_tags    | 商品标签  | 处理后   | 从 title 分离、去重、规范化、限制 ≤20 个        | 标签如"新品""热销""官方"等                |
| price           | 现价/售价 | 处理后   | 去货币符号、转 float、2 位小数、多币种转 RMB    | 重点：支持 USD/EUR 等转换                 |
| original_price  | 原价      | 处理后   | 同 price 处理，缺失标记 NULL                    | 市场指导价或原价                          |
| currency_code   | 货币代码  | 新增     | 标记原始货币(CNY/USD/EUR 等)                    | 用于审计和转换追踪                        |
| brand           | 品牌      | 原始     | 去特殊字符、统一大小写、建立标准库              | 品牌名标准化                              |
| category        | 分类      | 处理后   | 按层级分解(用">"分隔)、规范化分类树             | 如"手机>苹果>iPhone"                      |
| spec_params     | 规格参数  | 处理后   | 若为 String 解析为 JSON、规范化字段名、统一单位 | 技术类商品关键：CPU/内存/屏幕等 JSON 格式 |
| sales_volume    | 销量      | 处理后   | 去单位，换算为整数("1.5 万"→15000)              | 去除"件"等单位                            |
| comment_count   | 评论数    | 处理后   | 去单位，转整数                                  | 部分平台提供                              |
| rating          | 评分      | 处理后   | 转 float，限制 0-5，超出删除/修正               | 平均评分                                  |
| good_rate       | 好评率    | 处理后   | 转 float，限制 0-100%                           | 好评占比                                  |
| shop_name       | 店铺名    | 原始     | 去特殊字符、首尾空格，缺失填充"未知"            | 销售店铺                                  |
| shop_id         | 店铺 ID   | 原始     | 保留纯字母数字                                  | 店铺唯一标识                              |
| is_official     | 是否官方  | 原始     | 转布尔值(0/1)                                   | 官方旗舰店标记                            |
| listing_time    | 上架时间  | 处理后   | 相对时间 → 绝对时间，格式 YYYY-MM-DD HH:MM:SS   | 可能为"3 天前"                            |
| update_time     | 更新时间  | 处理后   | 统一格式 YYYY-MM-DD HH:MM:SS                    | 最后更新时间                              |

##### 特殊字段处理说明

**1. 标题与标签分离**

原始数据中标题可能含平台内嵌标记，需分离处理：

```
原始: 【官方旗舰店】Apple iPhone 15 Pro Max 256GB 新品热销

清洗后结果:
  - title: Apple iPhone 15 Pro Max 256GB
  - product_tags: ["官方旗舰店", "新品", "热销"]
  - is_official: 1 (标记为官方)
```

**2. 技术类商品规格参数**

如笔记本电脑需完整提取规格参数，规范为 JSON 格式：

```json
{
  "processor": "Intel Core i7-13700H",
  "ram": "16GB DDR5",
  "storage": "512GB SSD",
  "display": "15.6英寸 2.5K",
  "battery": "86Wh",
  "weight": "1.95kg"
}
```

新增评分字段 `spec_completeness` (0-100%) 用于评估规格完整度。

**3. 多币种价格转换**

详见后文"多币种价格转换处理方案"章节。

##### 多币种价格转换处理方案

**场景识别**：

```
抓取数据可能为：
  price: "$99.99" (美刀)
  or "€79.50" (欧元)
  or "¥599" (人民币)
  or "8999RMB"
```

**处理流程**：

1. **货币识别**

   - 提取货币符号或代码：$→USD, €→EUR, ¥→CNY 等
   - 记录到`currency_code`字段用于审计

2. **单位统一**

   - 去除货币符号和文字单位
   - 提取数字部分转为 float

3. **汇率转换**（如需转 RMB）

   ```python
   # 示例汇率配置（需定期维护）
   exchange_rates = {
       "USD": 7.08,   # 1美元 = 7.08人民币
       "EUR": 7.75,   # 1欧元 = 7.75人民币
       "GBP": 8.95,   # 1英镑 = 8.95人民币
       "JPY": 0.048,  # 1日元 = 0.048人民币
       "CNY": 1.0     # 已是人民币
   }

   # 转换逻辑
   price_rub = price_value * exchange_rates.get(currency_code, 1.0)
   ```

4. **异常处理**

   - 无法识别的货币 → 标记"currency_error"，保留原始价格
   - 汇率过期 → 标记"exchange_rate_outdated"
   - 价格为 0 或负数 → 标记"price_invalid"

5. **数据质量标记**
   ```
   字段: price_currency_info
   值示例: {
     "original_currency": "USD",
     "original_price": 99.99,
     "exchange_rate": 7.08,
     "converted_price_cny": 707.91,
     "conversion_date": "2024-01-08",
     "is_converted": true
   }
   ```

**数据库字段补充**：

| 字段名              | 类型       | 说明                         |
| ------------------- | ---------- | ---------------------------- |
| price               | Float      | 最终价格(已转 RMB，若需要)   |
| original_price      | Float      | 原始列表价格                 |
| currency_code       | Varchar(3) | 原始货币代码(USD/EUR/CNY 等) |
| price_currency_info | JSON       | 完整转换信息(含汇率/时间等)  |
| is_price_converted  | Boolean    | 是否已进行汇率转换           |

**常见问题与清洗方案**：

##### 分步骤清洗流程

**第一阶段：去重与关键字段验证**

| 问题类型        | 具体表现                      | 清洗方案                                                                                           | 执行步骤                                                               | 无法清洗处理                                                        |
| --------------- | ----------------------------- | -------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------- |
| 重复数据        | 同一 product_id 出现多次      | 按 product_id 去重，保留 update_time 最新的                                                        | 1. 按 product_id 分组 2. 统计重复数量 3. 保留 update_time 最大值       | 若无 update_time，按抓取时间保留最后一条                            |
| 缺失关键字段    | product_id、price、title 为空 | **准确性评估**：缺失必填字段无法补充 → 标记"critical_missing" → 删除记录                           | 1. 检验必填字段列表 2. 标记缺失类型 3. 删除无法补充的记录              | 直接删除，无补充途径                                                |
| product_id 缺失 | 商品无唯一标识                | **补充策略**：尝试由(source_platform, shop_id, title, listing_time)组合生成哈希值作为临时 ID       | 1. 组合字段生成哈希 2. 检验哈希唯一性 3. 添加标记"id_generated"        | 若组合字段也缺失或冲突，标记"id_supplement_failed"，待人工审核      |
| price 缺失      | 商品无价格信息                | **补充策略**：① 查询同店铺同品牌同类别商品的平均价格 ② 查询历史版本数据 ③ 标记"price_supplemented" | 1. 查同店/同品牌/同类别商品 2. 获取价格中位数 3. 补充价格并标记来源    | 无相似商品参考 → 标记"price_unavailable" → 按业务需求决定删除或保留 |
| title 缺失      | 商品无标题                    | **补充策略**：① 从 category 和 brand 拼接生成简易标题 ② 查询历史版本数据                           | 1. 组合 brand + category 生成标题 2. 标记"title_generated" 3. 手动验证 | 无品牌/分类信息 → 标记"title_unavailable" → 删除或待审核            |

**第二阶段：字段内容清洗与补充**

| 问题类型       | 具体表现                    | 清洗方案                                                      | 执行步骤                                                                           | 准确性评估                                                                                                              | 无法清洗处理                                                           |
| -------------- | --------------------------- | ------------------------------------------------------------- | ---------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 多币种价格     | $99.99 / €79.50 / ¥599      | 识别货币类型 → 查询汇率表 → 转换为 RMB                        | 详见"多币种价格转换处理方案"                                                       | **准确性检验**：① 汇率来源可靠性(央行汇率>99.5%) ② 转换日期与数据日期不超过 7 天 ③ 转换后价格合理性检验(不超出品类范围) | 无汇率或汇率过期>30 天 → 标记"exchange_rate_unavailable" → 保留原币种  |
| 标题内嵌标签   | 【官方旗舰店】iPhone 15 Pro | 从 title 提取平台标记 → 分离到 product_tags                   | 1. 正则匹配【】内容 2. 分离到 tags 2. 更新 title 3. is_official 置 1               | 检验提取是否完整，标签是否有效                                                                                          | 提取错误 → 保留原始 title，标记"tag_extract_error"                     |
| 规格参数不完整 | 技术类商品缺少关键参数      | **补充策略**：① 查同品牌同型号商品的规格 ② 从品牌官网爬取参数 | 1. 解析 spec_params JSON 2. 检验关键字段 3. 补充缺失参数 4. 评估 spec_completeness | **准确性评估**：补充参数的置信度评分(0-100%)：官网>99%, 同品牌>85%, 其他>60%                                            | 无法从其他源获取 → spec_completeness 评分 <70% → 标记"spec_incomplete" |
| 单位混乱       | 销量"1.5 万件"、"15000 件"  | 提取数字部分 → 单位转换(万 →\*10000) → 转整数                 | 1. 正则提数字 2. 识别单位 3. 单位转换 4. 转整数                                    | 转换结果是否合理(销量范围检验)                                                                                          | 无法识别单位格式 → 保留原始值，标记"sales_volume_invalid"              |

**第三阶段：异常值检测与修正**

| 问题类型   | 具体表现                  | 清洗方案                           | 执行步骤                                                    | 异常判定标准                 | 无法清洗处理                                           |
| ---------- | ------------------------- | ---------------------------------- | ----------------------------------------------------------- | ---------------------------- | ------------------------------------------------------ |
| 评分异常   | 5.5 分、0 分、-1 分、9 分 | 范围检验(0-5) → 超出范围则标记异常 | 1. 检验范围 2. 异常值标记"rating_invalid" 3. 可选删除或标记 | 标准范围 0-5，精度 0.1       | 无法确定正确值 → 标记"rating_unknown" → 根据好评率反推 |
| 好评率异常 | 120%、-50%、0%            | 范围检验(0-100%) → 超出范围标记    | 1. 检验范围 2. 若为百分比字符串先转数字 3. 标记异常         | 标准范围 0-100%              | 若为 0% → 检验是否真实(是否有评论)，为真实则保留       |
| 时间异常   | 时间早于商品上架时间      | 比对 publish_time 和 listing_time  | 1. 比对两个时间 2. 若早于上架时间标记异常                   | publish_time >= listing_time | 时间无法修正 → 标记"time_invalid"                      |

**第四阶段：文本清洗与编码处理**

| 问题类型 | 具体表现                 | 清洗方案                             | 执行步骤                                     | 验证方式                | 无法清洗处理                                       |
| -------- | ------------------------ | ------------------------------------ | -------------------------------------------- | ----------------------- | -------------------------------------------------- |
| 特殊字符 | 商品名含"❌""⚠️"等 emoji | 去除特殊字符和 emoji，保留中英文数字 | 1. 检测 emoji 和特殊符号 2. 删除 3. 验证结果 | 清洗后文本长度>0 且可读 | 全是特殊字符无实际内容 → 标记"title_invalid"       |
| 超长文本 | 商品名>500 字            | 截断至 200 字                        | 1. 检测长度 2. 超长则从前截断至 200 字       | 截断后是否包含完整信息  | 自行评估是否需要保留全文                           |
| 乱码问题 | 商品名出现乱码           | 尝试 chardet 库检测编码 → 重新解码   | 1. chardet 检测编码 2. 重新解码 3. 验证      | 解码后无乱码且可读      | 编码无法识别 → 标记"encoding_error" → 删除或待审核 |

##### 缺失值补充策略汇总

**分级补充方案**（按准确性从高到低）：

| 缺失字段        | 一级补充(高置信度>95%)               | 二级补充(中置信度 70-95%)     | 外部补充(低置信度<70%) | 补充失败处理                                |
| --------------- | ------------------------------------ | ----------------------------- | ---------------------- | ------------------------------------------- |
| **product_id**  | 源系统提供的备用 ID                  | 生成(platform+shop+title)哈希 | 使用内部序列号         | **无法补充** → 删除记录                     |
| **price**       | 当前时间段数据库同品牌同店铺商品     | 历史版本数据                  | 同分类平均价           | **标记 price_unavailable** → 按需删除或保留 |
| **title**       | 历史版本数据                         | 品牌官网+分类生成             | 分类+型号生成          | **标记 title_unavailable** → 删除或审核     |
| **category**    | 来源平台提供分类                     | 品牌标准分类库                | NLP 自动分类           | **标记 category_unknown** → 使用"其他"      |
| **spec_params** | 品牌官网规格                         | 同型号商品规格库              | 通用规格库             | **标记 spec_incomplete** → 评分<70%         |
| **shop_id**     | 源系统 shop_id                       | 店铺名查询店铺库              | 无法补充               | **标记 shop_unknown** → 保留 shop_name      |
| **good_rate**   | 从评论数据计算(comment 表 rating>=4) | 从 rating 反推                | 无法补充               | **标记 good_rate_unknown** → 留空           |

**准确性评估指标**（多维度综合评分）：

```
准确性评分公式：
  accuracy_score = \sum (field_weight × field_confidence) / \sum field_weight

其中：
  - field_weight：字段重要性权重(必填字段权重 1.0，可选字段 0.5)
  - field_confidence：每个字段的置信度(0-100%)

判定标准：
  accuracy_score >= 85%：数据质量优秀，可直接使用
  accuracy_score >= 70%：数据质量良好，可使用但需标记
  accuracy_score >= 50%：数据质量一般，需要审核后使用
  accuracy_score < 50%：数据质量差，不建议使用或删除
```

**存储建议**：

- 表名：`ec_product_info`
- 主键：`product_id`
- 索引：`(brand, category, listing_time)`
- 增加字段：`is_cleaned`（清洗标记）、`abnormal_tag`（异常标记）、`clean_time`（清洗时间）

**常见问题与清洗方案**:

##### 分步骤清洗流程

**第一阶段：去重与关键字段验证**

| 问题类型        | 具体表现                                             | 清洗方案                                                                            | 执行步骤                                                                        | 无法清洗处理                                    |
| --------------- | ---------------------------------------------------- | ----------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- | ----------------------------------------------- |
| 重复评论        | 相同 comment_id 或(product_id, user_id, content)重复 | 按 comment_id 去重，或按(product_id, user_id, comment_content)组合判断完全重复；**二级评论**：允许相同内容但不同 parent_comment_id（回复上下文不同）| 1. 按 comment_id 分组统计 2. 检测组合重复 3. 一级评论保留最新，二级评论每个父评论可重复 | 若无 comment_id，按组合去重，标记"id_generated" |
| comment_id 缺失 | 评论无唯一标识                                       | **补充策略**：由(product_id, user_id, comment_content, comment_time, comment_level, parent_comment_id)组合生成哈希 ID | 1. 二级评论必须包含 parent_comment_id 2. 生成哈希值 3. 检验唯一性 4. 标记"id_generated"  | 组合字段也缺失 → 标记"critical_missing" → 删除  |
| product_id 缺失 | 评论无关联商品                                       | **补充策略**：二级评论无需 product_id（继承父评论）；一级评论从相邻推断或标记缺失                         | 1. 判断 comment_level 2. 二级评论跳过此步 3. 一级评论查询相邻 4. 标记来源       | 无法推断 → 标记"product_id_unavailable" → 删除  |
| user_id 缺失    | 匿名用户评论                                         | **补充策略**：填充"anonymous_user" + 哈希(user_name + comment_content + comment_level) | 1. 检查 user_name 2. 生成临时 user_id 3. 标记"user_anonymous"                   | 保留为"未知"用户                                |
| parent_comment_id 缺失(二级) | 二级评论不指向父评论 | **验证策略**：检查 parent_comment_id 是否存在有效的一级评论；形成循环引用检测 | 1. 查询 parent_comment_id 是否存在 2. 检查回环 3. 推断或匹配父评论 4. 标记来源 | 所属一级评论不存在 → 标记"orphan_comment" → 删除 |

**第二阶段：字段内容清洗与补充**

| 问题类型 | 具体表现                                    | 清洗方案                                                         | 执行步骤                                                       | 准确性评估                         | 无法清洗处理                                  |
| -------- | ------------------------------------------- | ---------------------------------------------------------------- | -------------------------------------------------------------- | ---------------------------------- | --------------------------------------------- |
| 文本污染 | HTML 标签、表情符号、@用户、URL 链接        | 去 HTML 标签 → 去表情 → 去@用户 → 去 URL 链接                    | 1. BeautifulSoup 去 HTML 2. 正则去 emoji 3. 去@提及 4. 去链接  | 清洗后文本长度>0 且可读            | 全是污染内容 → 标记"content_invalid"          |
| 评论过短 | comment_content<10 字                       | 检测并标记，可选删除                                             | 1. 计算文本长度 2. 标记"content_too_short"                     | 是否有实际意义(如"好""赞"也有价值) | 根据业务规则决定删除或保留                    |
| 垃圾评论 | 刷屏重复字符（"哈哈"×50）、纯广告、无关评论 | **检测模式**：① 连续重复字符>80% ② 包含推广链接 ③ 与商品完全无关 | 1. 检测重复率 2. 识别广告关键词 3. NLP 相关性检测 4. 标记/删除 | 识别准确度需>85%                   | 无法确定 → 标记"spam_suspicious" → 待人工审核 |

**第三阶段：异常值检测与修正**

| 问题类型           | 具体表现                           | 清洗方案                                     | 执行步骤                                | 异常判定标准                                        | 无法清洗处理                           |
| ------------------ | ---------------------------------- | -------------------------------------------- | --------------------------------------- | --------------------------------------------------- | -------------------------------------- |
| 评分异常           | 6 分、0 分、负数、非整数           | 范围检验(1-5) → 超出范围标记"rating_invalid" | 1. 检验范围 2. 转整数 3. 标记异常       | 标准范围 1-5，仅限整数                              | 无法确定正确值 → 标记"rating_unknown"  |
| helpful_count 异常 | 负数、超百万                       | 范围检验(≥0, <1000000)                       | 1. 检验范围 2. 异常值标记               | 标准范围 0-1000000                                  | 无法修正 → 标记"helpful_count_invalid" |
| 时间异常           | 时间早于商品上架时间或晚于当前时间 | 比对 comment_time 与 product listing_time    | 1. 比对两个时间 2. 范围校验 3. 标记异常 | comment_time >= product.listing_time 且 <= 当前时间 | 时间无法修正 → 标记"time_invalid"      |

**第四阶段：文本清洗与编码处理**

| 问题类型 | 具体表现             | 清洗方案                           | 执行步骤                                             | 验证方式             | 无法清洗处理                               |
| -------- | -------------------- | ---------------------------------- | ---------------------------------------------------- | -------------------- | ------------------------------------------ |
| 乱码文本 | 评论内容出现乱码字符 | chardet 检测编码 → 重新解码 → 验证 | 1. chardet 检测 2. 重新解码 3. 验证可读性            | 解码后无乱码且可读   | 编码无法识别 → 标记"encoding_error" → 删除 |
| 超长评论 | 超过 10000 字        | 截断至 10000 字                    | 1. 检测长度 2. 超长则截断 3. 标记"content_truncated" | 截断是否损失关键信息 | 自行评估是否需要全文保留                   |

##### 缺失值补充策略汇总

**分级补充方案**（按准确性从高到低）：

| 缺失字段          | 一级补充(高置信度>95%) | 二级补充(中置信度 70-95%)                | 外部补充(低置信度<70%) | 补充失败处理                                   |
| ----------------- | ---------------------- | ---------------------------------------- | ---------------------- | ---------------------------------------------- |
| **comment_id**    | 源系统原始 ID          | 生成(product_id + user_id + content)哈希 | 使用内部序列号         | **无法补充** → 删除记录                        |
| **product_id**    | 源系统 product_id      | 查询相邻评论推断                         | 无法推断               | **标记 product_id_unavailable** → 删除         |
| **user_id**       | 源系统 user_id         | 生成(user_name + content 哈希)           | 填充"anonymous"        | **标记 user_anonymous** → 保留                 |
| **rating_score**  | 原始评分               | 从其他相邻评论推断平均值                 | 无法推断               | **标记 rating_unknown** → 留空或使用平台平均分 |
| **comment_time**  | 源系统时间             | 相邻评论推断                             | 使用爬取时间           | **标记 time_unknown** → 使用爬取时间           |
| **parent_comment_id(二级专用)** | **N/A(一级此字段为NULL)** | 从每一级评论查询推断 | 无法推断 | **标记 orphan_comment** → 删除 |

**准确性评估指标**（评论质量评分）：

```
准确性评分公式：
  comment_quality_score = \sum (field_weight × field_confidence) / \sum field_weight

其中：
  - field_weight：字段重要性权重
    * comment_id: 1.0 (必填)
    * product_id: 1.0 (必填)
    * rating_score: 0.8 (重要) -> **一级评论可有**；**二级评论不需武**
    * comment_content: 0.9 (核心)
    * comment_time: 0.6 (可选)
    * helpful_count: 0.3 (可选) -> **二级评论易提取回复数**
    * parent_comment_id: 0.5 (二级专用) -> **一级评论为NULL**
    * comment_level: 0.4 (区分一二级)
  - field_confidence：每个字段的置信度(0-100%)

判定标准：
  score >= 80%：优质评论，可直接使用
  score >= 60%：良好评论，可使用但需标记
  score >= 40%：一般评论，需要审查
  score < 40%：低质评论，不建议使用或删除

二级评论需有效 parent_comment_id 及 parent 评论本身有效，悬浮评论（孤立的二级）会预 10-30% 的分数功能值。
```

**存储建议**：

- 表名：`ec_comment`
- 主键：`comment_id`
- 索引：
  * `(product_id, rating_score, comment_date)` - 一级评论优化
  * `(parent_comment_id)` - 二级评论上游索引
  * `(comment_level, parent_comment_id)` - 评论树查询优化
- 外键：
  * `product_id → ec_product_info.product_id`
  * **`parent_comment_id → ec_comment.comment_id` (二级评论自引用)
- **分区：**二级评论不需单独分区，可按 comment_level 滑动

##### 特殊字段处理说明

**1. 平台处理统一性**

不同平台需要按规范转换标准：

```
平台   user_id格式    user_name    comment_time
微博   整数       @昵称      2024-01-08 15:30:00
知乎   字母数字  昵称      相对时间传绝对
小红书 整数      昵称      相对时间
```

**2. 文本污染清洗**

各平台需去除特定污染：

- 微博：#话题#、转发、@用户
- 知乎：分类信息、@用户
- 小红书：商品推广、微商代理

**3. 垃圾评论模式**

检测：高频重复字符、纯外部链接、客服联系、上下文完全不相关

**常见问题与清洗方案**：

##### 分步骤清洗流程

**第四阶段：文本清洗与编码处理**

| 问题类型 | 具体表现             | 清洗方案                                                  | 执行步骤                                                                      | 验证方式                 | 无法清洗处理                               |
| -------- | -------------------- | --------------------------------------------------------- | ----------------------------------------------------------------------------- | ------------------------ | ------------------------------------------ |
| 乱码文本 | 评论内容出现乱码字符 | 使用 chardet 检测原始编码 → 重新解码为 UTF-8 → 验证可读性 | 1. chardet 检测编码 2. 按检测编码解码 3. 验证汉字可读性 4. 失败则尝试其他编码 | 解码后不含乱码且汉字可读 | 编码无法识别 → 标记"encoding_error" → 删除 |

##### 缺失值补充策略汇总

**分级补充方案**（按准确性从高到低）：

| 缺失字段         | 一级补充(>95%)    | 二级补充(70-95%)                  | 外部补充(<70%)  | 补充失败处理                      |
| ---------------- | ----------------- | --------------------------------- | --------------- | --------------------------------- |
| **comment_id**   | 源系统 comment_id | 生成(post_id+user_id+content)哈希 | 序列号+platform | **无法补充** → 删除               |
| **post_id**      | 源系统 post_id    | HTTP Referer 推断                 | 相邻评论推断    | **无法补充** → 删除               |
| **user_id**      | 源系统 user_id    | 从 user_name 生成临时 ID          | 填充"anonymous" | **标记 user_anonymous**，保留备注 |
| **like_count**   | 原始互动数        | 相似内容平均值                    | 填充 0          | **标记 like_count_unknown**       |
| **comment_time** | 源系统时间戳      | 相对时间转绝对                    | 填充发布日期    | **标记 time_uncertain**           |

**准确性评估指标**：

```
comment_quality = Σ(field_weight × field_confidence) / Σfield_weight

字段权重分配：
  comment_id: 1.0 (必填)
  post_id: 1.0 (必填)
  user_id: 0.8 (关键)
  comment_content: 0.9 (关键)
  like_count: 0.4 (可选)
  comment_time: 0.6 (重要)
  platform: 0.5 (辅助)

  >= 80%: 优质评论，可直接使用

```

**存储建议**：

- 表名：`social_comment`
- 主键：`comment_id`
- 索引：`(post_id, user_id, comment_time, platform)`
- 全文索引：`comment_content`
- 分区：按 platform + comment_date

##### 特殊字段处理说明

**1. 转载重复检测**

```
检测方式：
  1. 标题相似度 > 90% 标记为转载
  2. 内容相似度 > 85% 标记为转载
  3. 保留首发源，备份其他版本
```

**2. 文本污染清洗**

需去除的污染内容：

- HTML 标签和脚本
- 文末推广段落
- 广告链接（超过 30%标记 marketing）
- 无关段落和水印

**3. 分类和标签规范**

```
Category规范化：
  原始: "科技 > 互联网" 或 "科技,互联网"
  处理后: "科技>互联网" (用">"分隔)

Tag规范化：
  分解多值："python,AI,机器学习" -> ["python", "AI", "机器学习"]
  去重、规范化、限制≤15个
```

## 清洗流程通用方案

无论处理何种数据类型，清洗流程统一遵循以下 **5 大核心步骤**：

### 步骤 1：明确清洗目标

- 查看元数据清单，确定`must_clean_fields`（必清洗字段）
- 查看业务字典中的`field_standard_rule`（标准化规则）
- 聚焦核心字段，避免无效处理

### 步骤 2：去重处理

- 按唯一标识（如商品 ID、评论 ID）进行精准去重（优先级最高）
- 检测完全重复记录（所有字段内容一致）
- 生成去重统计报告

### 步骤 3：字段标准化

- **文本字段**：去空格、去特殊字符、统一编码、统一大小写
- **数值字段**：去单位、转为标准类型、范围校验
- **时间字段**：相对 → 绝对、统一格式、时间戳校验
- **分类字段**：规范化值、建立标准库、多值处理
- **URL/链接**：格式验证、失效检测

### 步骤 4：缺失值处理

- **核心字段**：缺失率低 → 删除记录，缺失率高 → 标注"待补充"
- **非核心字段**：填充"未知"、众数、中位数或 NULL
- 记录缺失统计

### 步骤 5：异常值修正

- **数值异常**：检测业务逻辑合理范围，用中位数/平均值修正，极端异常删除
- **格式异常**：尝试修复格式，无法修复则删除或标注
- **内容异常**：检测垃圾内容、广告内容，直接剔除或标记
- **关系异常**：如资产 ≠ 负债+权益，检测并标记

#### 多币种价格转换处理方案

**场景识别**：

```
抓取数据可能为：
  price: "$99.99" (美刀)
  or "€79.50" (欧元)
  or "¥599" (人民币)
  or "8999RMB"
```

**处理流程**：

1. **货币识别**

   - 提取货币符号或代码：$→USD, €→EUR, ¥→CNY 等
   - 记录到`currency_code`字段用于审计

2. **单位统一**

   - 去除货币符号和文字单位
   - 提取数字部分转为 float

3. **汇率转换**（如需转 RMB）

   ```python
   # 示例汇率配置（需定期维护）
   exchange_rates = {
       "USD": 7.08,   # 1美元 = 7.08人民币
       "EUR": 7.75,   # 1欧元 = 7.75人民币
       "GBP": 8.95,   # 1英镑 = 8.95人民币
       "JPY": 0.048,  # 1日元 = 0.048人民币
       "CNY": 1.0     # 已是人民币
   }

   # 转换逻辑
   price_rub = price_value * exchange_rates.get(currency_code, 1.0)
   ```

4. **异常处理**

   - 无法识别的货币 → 标记"currency_error"，保留原始价格
   - 汇率过期 → 标记"exchange_rate_outdated"
   - 价格为 0 或负数 → 标记"price_invalid"

5. **数据质量标记**
   ```
   字段: price_currency_info
   值示例: {
     "original_currency": "USD",
     "original_price": 99.99,
     "exchange_rate": 7.08,
     "converted_price_cny": 707.91,
     "conversion_date": "2024-01-08",
     "is_converted": true
   }
   ```

本文档已对所有业务类型（1.1 至 10）进行了详细优化，现在所有"常见问题与清洗方案"部分均包含以下四个阶段的分步骤清洗流程：

#### 应用新模板的标准结构（4 大阶段）

**第一阶段：去重与关键字段验证**

- 特殊内容检测（如垃圾评论、广告）

**第三阶段：异常值检测与修正**

- 数值范围校验
- 异常判定标准

**第四阶段：文本清洗与编码处理**

- 乱码文本处理
- 超长内容处理
- 特殊字符处理

#### 缺失值补充策略汇总（按字段类型）

每个业务类型都包含一个分级补充方案表，采用以下外部补充策略：

- **一级补充(>95%)**: 源系统原始数据或官方数据
- **二级补充(70-95%)**: 从相关数据推断或部分补充
- **外部补充(<70%)**: 通用默认值或最后手段
- **补充失败处理**: 标记异常、删除 or 待审核

#### 准确性评估指标（多维度评分）

每个业务类型都包含准确性评分公式，例如：

```
quality_score = \sum (field_weight × field_confidence) / \sum field_weight

判定标准（通用）：
  >= 85%: 优秀，可直接使用
  >= 70%: 良好，可使用但需标记
  >= 50%: 一般，需要审核
  < 50%: 较差，不建议使用或删除
```

在实际应用中，所有业务类型已完成标准化优化。清洗引擎应根据 `accuracy_score` 自动执行以下逻辑：

2. **人工抽检**：`70% <= accuracy_score < 85%` 的记录定期进行人工抽检，验证补充策略的有效性。
3. **专家审核**：`50% <= accuracy_score < 70%` 的记录需进入审核队列，由业务专家确认后导入。
4. 自动过滤：accuracy_score < 50% 的记录直接进入异常库，不参与后续业务分析。
